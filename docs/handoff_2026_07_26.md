## 2. The root problem this session existed to fix

The customer said "LeadMe integration is unreliable — works for a
while, then breaks. Status changes and slot tags randomly don't land."
Their intuition was that cookies were dying. **The reality was worse:
we had two distinct failure modes stacked on top of each other**,
neither properly monitored.

### 2.1. The CTWA phone-lookup race (the big one)

Diagnostic on production (`docker logs propeller_bot --since 48h |
grep push_lead`) showed:

| Metric (48 h window)                            | Count |
|-------------------------------------------------|------:|
| `push_lead` calls that succeeded                | **4** |
| `push_lead` calls dropped as "not found after 4 attempts" | **40** |
| Failed admin API writes (HTTP/JSON errors)      | **0** |
| Slot tags (`חלון · <slot>`) pushed in 7 days   | **0** |

Root cause: Facebook / TikTok CTWA leads reach the bot faster than
LeadMe's own supplier sync updates its DB. Old code retried the phone
lookup **4 times over 30 seconds** inside the request path, then gave
up **forever**. The lead stayed at `חדש` in LeadMe permanently and
the sales team never saw the engagement level or call-window tag.

### 2.2. Cookies dying

`csrf_cookie_name` has hard `Max-Age=86400` — dies every 24 hours
regardless of activity. When it dies, everything below it silently
returns HTML login pages that our old error handling logged as generic
"non-JSON parse error" — indistinguishable from any other bug.

### 2.3. Silent bug family

Along the diagnostic path I found four bugs in the existing code that
all had one thing in common: **they succeed silently on failure**.
See §5 for the full list — this is the most important section of this
document.

## 4. New module walk-throughs (short version)

### 4.1. `crm/leadme_queue.py` — the retry queue

State lives on `lead.lead_metadata` (no new DB table, no migration):

```python
{
    "leadme_push_pending": [
        {"kind": "engagement", "level": 1, "slot": "9-12", "note": "..."},
        {"kind": "ctwa_tag", "campaign": "עודד"},
    ],
    "leadme_push_next_attempt_at": "2026-07-26T10:25:00+00:00",
    "leadme_push_attempts": 3,
    "leadme_push_queued_at": "2026-07-26T10:12:00+00:00",
    # After 60 minutes with no success:
    "leadme_push_abandoned": True,
    "leadme_push_abandoned_at": "2026-07-26T11:12:00+00:00",
    "leadme_push_abandoned_items": [...],
}
```

Rules:

- **Merge, don't overwrite**: `enqueue_engagement` folds a new item
  into any existing engagement entry. Lower level wins (1 = booked
  beats 2 = replied beats 3 = silent). Slots and notes are preserved.
- **`ctwa_tag` items dedupe on `campaign`**. A second `מקור: עודד`
  enqueue for the same lead is a no-op.
- **Retries every `LEADME_QUEUE_INTERVAL_MINUTES`** (default 3, linear).
- **Give up after `MAX_LIFETIME_MINUTES` = 60** (or `MAX_ATTEMPTS` = 20,
  whichever hits first). On give-up, log `ERROR` + set
  `leadme_push_abandoned`.
- **Abandoned items are visible in `/admin/leadme-status`** and can be
  manually re-triggered with the "שיחזור" button.

Public API from the scheduler side: `retry_pending_pushes()` (drain
one tick) and `get_queue_snapshot()` (read-only introspection for the
admin UI).

### 4.2. `crm/leadme_client.py::check_leadme_session_health()`

Returns one of `{healthy | expired | unreachable | no_cookies}` with a
Hebrew-friendly `detail` string. 30-second in-process cache so the
admin pill on every page load is cheap.

- `healthy`: `GET /app/leads` returned 200 + response contains
  `"LeadMe CMS |"` marker (their admin title).
- `expired`: 200 but body contains reCAPTCHA / password-input markers
  — LeadMe returned the login page.
- `unreachable`: HTTP error, non-200, or network exception.
- `no_cookies`: `LEADME_COOKIES_PATH` empty/missing/malformed.

Bust the cache with `force=True` (admin "רענן בדיקה" button, scheduler
tick).

### 4.3. `crm/leadme_login.py` — auto-refresh (2Captcha)

Pure httpx + 2Captcha, no browser dependencies:

1. `GET /login` → capture `PHPSESSID` + `csrf_cookie_name` cookies +
   extract `csrf_lmcms` hidden input + reCAPTCHA sitekey.
2. Submit sitekey + page URL to 2Captcha (`http://2captcha.com/in.php`),
   poll `res.php` every 5 s (cap at 3 min). Cost ~$0.003 per solve.
3. `POST /login/verifyLogin` with `email`, `password`, `csrf_lmcms`,
   `g-recaptcha-response`, `checkbox-inline=on`.
4. Follow the redirect, verify by hitting `/app/leads` and matching
   the admin marker.
5. **Atomic write**: `tmp = path + ".tmp"; tmp.write_text(...);
   tmp.replace(path)`. A crash mid-write can never leave a truncated
   cookies file behind.
6. **Never overwrites** working cookies on failure — the existing
   session keeps working until it dies naturally.
7. Busts the health-check cache on success so the admin panel + queue
   drainer pick up the fresh session immediately.

Triggered from three places:
- Proactive: scheduler job every `LEADME_AUTO_REFRESH_INTERVAL_HOURS`
  (default 12), only registered when `LEADME_AUTO_REFRESH_ENABLED=true`.
- Reactive: `_leadme_session_health_tick` fires it immediately when
  health flips to `expired` or `no_cookies` and auto-refresh is enabled.
- Manual: "רענן עכשיו" button on `/admin/leadme-cookies` (synchronous
  — browser waits for 2Captcha).

### 4.4. Admin UI additions

- **Header pill on every admin page** — green/orange/red LeadMe status.

## 5. Anti-patterns I caught (⚠ DO NOT RE-INTRODUCE)

The following are all things that were in the codebase before this
session started. Each one was actively causing bugs. If you see a
future change that reintroduces any of these patterns, push back.

### 5.1. Silent fallback in ID resolution

**Bad (before):**
```python
def _resolve_tag_lead_id(client, lc_id: str) -> str:
    try:
        resp = client.get(base + f"/app/leads/viewLead/{lc_id}")
        match = re.search(r"uploadLeadProfileImage\((\d+)\)", resp.text)
        if match:
            return match.group(1)
    except Exception:
        pass
    return lc_id  # ← FALLBACK TO WRONG ID
```

Why it's terrible: `addLeadTag` accepts `result:true` when given the
WRONG id (it needs the internal `leadId` in the 13xxxxxx range, not
the `lc_id` in the 22xxxxxx range). So the tag never lands on the
lead but the log shows success. Debugging becomes impossible.

**Good (after):**
```python
def _resolve_tag_lead_id(client, lc_id: str) -> Optional[str]:
    # ... on any failure ...
    logger.warning("[LeadMe] viewLead page for lc_id=... did not "
                   "contain internal leadId ...")
    return None
```

**Rule:** When an external API accepts anything on success but silently
no-ops on wrong ID, you MUST return `None` on parse failure and force
the caller to skip the write. Never fall back to a "close enough" ID.

### 5.2. Foot-guns that recreate deleted-for-a-reason bugs

We removed all `/supplier/insert` and `/supplier/update` calls on
2026-07-22 because they act as UPSERT and leak duplicates into
campaign 12277 ("הוסרו מ-Whatsapp"). But an old helper survived:

**Bad (before):**
```python
def _push_slot_tag_via_api(phone: str, tag: str) -> bool:
    """Add a slot tag via the public supplier/insert API..."""
    resp = httpx.post(url, data={
        "action": "new_lead",
        "phone": phone,
        "tags": tag,
    }, ...)
```

It was unused. It survived because the removal PR was tactical, not
strategic. If a future refactor "resurrects" this function to handle
some edge case, it will silently leak leads into 12277 and the
`_campaign_leak_canary` will start firing every hour.

**Rule:** Deleted-for-a-reason code stays deleted. If someone finds it
in `git log` and thinks "oh this looks useful", check the commit that
removed it before restoring. Same rule applies to `LEADME_INSERT_URL`
and `LEADME_UPDATE_URL` env vars — they are relics kept for
back-compat but MUST NOT be used to build URL strings in new code.

### 5.3. Parameter shadowing

**Bad (before):**
```python
def push_lead(lead, note=None, level=1, slot=None):  # ← accepts slot
    ...
    slot = (lead.lead_metadata or {}).get("preferred_call_slot")  # ← ignores it
    if slot: ...
```

Callers passed `slot="9-12"` expecting it to be used. It wasn't —
the function immediately overrode from metadata. The bug was masked
because in practice callers ALSO wrote the slot to metadata, so
things looked fine most of the time.

**Good (after):** parameter removed from `push_lead`. Kept on
`push_engagement_level(slot=)` as accepted-but-explicitly-ignored
(with a debug log) for back-compat with old callers.

**Rule:** If a function reads from metadata as source-of-truth, don't
also accept the same value as an argument. Pick one. If you must
accept both, document which wins and log if the caller's value is
being discarded.

### 5.4. In-request retry loops for external dependencies

**Bad (before):**
```python
for attempt in range(4):
    row = get_row_by_phone(lead.phone, client)
    if row is not None:
        break
    if attempt < 3:
        time.sleep((attempt + 1) * 5)  # 5, 10, 15 seconds
```

30 seconds inside a synchronous handler. If LeadMe's supplier-sync is
slow, the WHOLE bot response to the user waits 30 s or drops the update
forever. That's the CTWA race.

**Good (after):** 2 fast retries (~10 s max), then queue and return
success. Background scheduler handles the long tail (up to 60 min).

**Rule:** Any external system that has a "eventually consistent" latency
distribution belongs in a background queue, not an in-request retry
loop. Cap in-request retries at ~10-15 seconds total.

### 5.5. Dead code paths that whisper "still works"

**Bad (before):**
```python
def push_lead_cancellation(lead, reason=None):
    ...
    ok_tag = True  # ← never actually set to anything else
    ok_status = _admin_change_status(client, leadme_id, "1")
    logger.info("... tag_ok={} status_ok={}", ok_tag, ok_status)
    return ok_tag or ok_status
```

`ok_tag` was a leftover from when we pushed a "ביטול שיחה" tag. The
tag was removed but the variable stayed. `return ok_tag or ok_status`
now always returns True, which is fine — but the log line lies to
whoever's reading it.

**Rule:** When you remove functionality, remove ALL references, not
just the API call. Grep for the old variable, remove its declaration,
remove it from log strings, remove it from return values.

### 5.6. Non-differentiated error logging

**Bad (before):**
```python
try:
    body = resp.json()
except Exception:
    logger.warning("non-JSON for leadme_id={}: {!r}", leadme_id, resp.text[:200])
    return False
```

"Non-JSON" happens for at least three reasons: session expired,
endpoint moved, request payload malformed. Same log line for all
three.

**Good (after):**
```python
except Exception:
    preview = resp.text[:200]
    looks_like_login = "login" in preview.lower() or "recaptcha" in preview.lower()
    logger.warning(
        "[LeadMe admin status] non-JSON for leadme_id={} "
        "(likely_session_expired={}): {!r}",
        leadme_id, looks_like_login, preview,
    )
```

**Rule:** When a single failure mode has multiple likely causes, do at
least one distinguishing check in the error path and put it in the
log line. `grep likely_session_expired=True docker.log` is
infinitely more useful than `grep non-JSON docker.log`.

### 5.7. Confusing IDs that share a type

LeadMe uses `str` for both `lc_id` (22xxxxxx) and internal `leadId`
(13xxxxxx). Nothing in Python catches "you passed lc_id to a function
expecting leadId" because they're both strings. This wasted half a
day chasing a bug where tags "worked" (`result:true`) but never
appeared.

**Rule for LeadMe specifically:** in this repo, treat these as
distinct concepts. When a function takes an ID, name the parameter
after which one it wants:
- `_admin_change_status(client, lc_id, status_id)` — uses `lc_id`
- `_admin_add_tag(client, internal_leadId, tag)` — uses `internal_leadId`
- `_resolve_tag_lead_id(client, lc_id) -> Optional[str]` — converts

If you introduce a new admin endpoint, document which ID it expects.
Cross-check with what `docs/leadme_integration.md` §5.2 says.

### 5.8. Trusting HTTP 200

LeadMe's admin endpoints return **HTTP 200 for both success and silent
failure**. `changeLeadsStatus` returns `{"result": true, "msg": "..."}`
on success and `{"result": false, "msg": "לא נבחרו רשומות!"}` on
failure — both with HTTP 200.

**Rule:** For LeadMe writes, `resp.status_code == 200` is a NECESSARY
but not SUFFICIENT check. You MUST also `resp.json().get("result") is
True`. This is why every admin helper in `leadme_client.py` looks like:

```python
if resp.status_code != 200: return False
body = resp.json()  # may raise if HTML -> caught, logged
if not body.get("result"): return False
return True
```

Don't shortcut this.

## 8. Common pitfalls & how to debug

### Symptom: "I see leads in the queue but they never drain"

Check in this order:
1. `docker logs propeller_bot 2>&1 | grep "leadme_queue_drain"` —
   is the scheduler job even running? Should fire every 3 min.
2. Session health — if `expired`, drainer can't authenticate. Fix
   cookies first (§7.2, §7.6).
3. `docker exec propeller_bot python3 -c "from app.crm.leadme_delete
   import _build_client, get_row_by_phone; c = _build_client();
   print(get_row_by_phone('<phone>', c))"` — is the phone visible in
   LeadMe yet? If `None`, LeadMe still hasn't synced from Facebook.
   Nothing we can do until it does.
4. Attempts > `MAX_ATTEMPTS` (20)? Look for `[leadme-queue] ABANDONING`
   in the logs.

### Symptom: "Tag POST returns result:true but tag doesn't show up"

You sent `lc_id` (22xxxxxx) to `addLeadTag` instead of the internal
`leadId` (13xxxxxx). Route it through `_resolve_tag_lead_id(client, lc_id)`
first. Note the return type is `Optional[str]` — check for None.

### Symptom: "Bot reports success but LeadMe pill still shows חדש"

Two possibilities:
1. `docker logs | grep "LeadMe admin status"` — do you see the actual
   POST log line with `result: true`? If not, `push_lead` was called
   but never reached the status POST — check `push_lead` guards (test
   phone, banned campaign, kill switches).
2. Cache: LeadMe UI sometimes takes a second to refresh. F5 the page.

### Symptom: "2Captcha auto-refresh always fails"

Check `docker logs | grep "leadme-login"`. The failure reason is in
the log:
- `LEADME_LOGIN_EMAIL / LEADME_LOGIN_PASSWORD not set` → set them in `.env`.
- `LEADME_CAPTCHA_API_KEY not set` → set it in `.env`.
- `2Captcha refused submit: {...}` → 2Captcha rejected the request.
  Common causes: no balance (top up at 2captcha.com/enterpage),
  invalid key.
- `2Captcha timed out after 180s` → 2Captcha couldn't solve. Retry
  once; if it recurs, LeadMe may have upgraded to reCAPTCHA v3 —
  we'd need to change the module.
- `post-login verification failed: got login/reCAPTCHA page back` →
  password wrong, or LeadMe added an extra challenge (e.g. 2FA).
